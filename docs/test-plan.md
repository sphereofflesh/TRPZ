## 1. Мета та об'єкт тестування

Мета — перевірити, що Web API застосунку `Labka` коректно віддає дані прогнозу погоди, відповідає узгодженому контракту та коректно поводиться в Development- і Production-середовищах.

Об'єкт тестування — HTTP-ендпоінт(и), оголошені в `Labka/Program.cs`:

| Метод | Шлях | Призначення | Обробник |
| --- | --- | --- | --- |
| GET | `/weatherforecast` | Повертає масив із 5 випадкових прогнозів | `GetWeatherForecast` |

Контракт елемента масиву (запис `WeatherForecast`):

| Поле (JSON) | Тип | Обмеження / правило |
| --- | --- | --- |
| `date` | string (`yyyy-MM-dd`) | 5 послідовних діб, починаючи з наступної від поточної |
| `temperatureC` | int | випадкове в діапазоні `[-20; 54]` |
| `summary` | string | одне зі значень: `Freezing`, `Bracing`, `Chilly`, `Cool`, `Mild`, `Warm`, `Balmy`, `Hot`, `Sweltering`, `Scorching` |
| `temperatureF` | int | обчислюється як `32 + (int)(temperatureC / 0.5556)` |

## 2. Обсяг

**У межах тестування:**

- коректність HTTP-статусів, заголовків і формату тіла відповіді ендпоінта `/weatherforecast`;
- відповідність даних контракту (кількість елементів, склад і типи полів, діапазони, узгодженість `temperatureC` ↔ `temperatureF`);
- доступність Swagger UI та OpenAPI-схеми в Development;
- поведінка за помилкових запитів (невідомий маршрут, непідтримуваний метод);
- поведінка за `ASPNETCORE_ENVIRONMENT=Production`;
- базова перевірка продуктивності (smoke).

**Поза межами тестування (на поточній ітерації):**

- навантажувальне та стрес-тестування;
- тестування безпеки (автентифікація, авторизація, вразливості);
- тестування UI: власного інтерфейсу, крім згенерованого Swagger UI, у застосунку немає;
- перевірка CI/CD-конвеєра (зона відповідальності Ткаченка Богдана);
- сумісність із базами даних — застосунок не має шару збереження даних.

| Компонент | Значення |
| --- | --- |
| ОС | Windows 11 Home Single Language, 10.0.26300, x64 |
| Платформа | .NET SDK 8.0.426, ASP.NET Core Runtime 8.0.32 |
| Збірка | `main` @ `ad3c395`, конфігурація Debug, цільова платформа net8.0 |

```powershell

# Production, використовується для TC-10
$env:ASPNETCORE_ENVIRONMENT = "Production"

```

## 4. Підхід і рівні тестування

| Рівень | Що перевіряємо | Спосіб |
| --- | --- | --- |
| Димове тестування (smoke) | застосунок стартує, ендпоінт відповідає | ручний запит `curl` |
| Функціональне тестування | статуси, структура та вміст відповіді | ручні запити + `jq`/PowerShell |
| Контрактне тестування | відповідність OpenAPI-схемі | Swagger UI, `swagger.json` |
| Негативне тестування | невідомі маршрути, непідтримувані методи | ручні запити |
| Конфігураційне тестування | поведінка в Development і Production | зміна `ASPNETCORE_ENVIRONMENT` |
| Приймальне тестування | виконання критеріїв приймання (розділ 7) | прогін усіх тест-кейсів |

Тестування виконується вручну (застосунок не має автоматичних тестів). Юніт-тести та інтеграційні тести на цій ітерації не реалізовані — це зафіксовано як ризик у розділі 10.

## 5. Тестові дані

Окремі тестові дані не потрібні: ендпоінт не приймає вхідних параметрів і не має тіла запиту. Значення генеруються випадково під час обробки запиту, тому перевіряються інваріанти (діапазони, склад полів, узгодженість), а не конкретні значення.

## 6. Тест-кейси

Пріоритети: **P1** — блокуючі для приймання, **P2** — важливі, **P3** — додаткові.

| ID | Пріоритет | Назва | Кроки | Очікуваний результат |
| --- | --- | --- | --- | --- |
| TC-01 | P1 | Ендпоінт доступний | `GET http://localhost:5052/weatherforecast` | `200 OK`, `Content-Type: application/json` |
| TC-02 | P1 | Кількість елементів | `GET /weatherforecast`, порахувати елементи масиву | Рівно **5** елементів |
| TC-03 | P1 | Склад полів | Перевірити ключі кожного елемента | У кожному елементі присутні `date`, `temperatureC`, `summary`, `temperatureF` |
| TC-04 | P1 | Формат і послідовність дат | Звірити `date` з поточною датою | Дати у форматі `yyyy-MM-dd`, 5 послідовних діб від «завтра» до «+5 діб», за зростанням, без пропусків |
| TC-05 | P1 | Діапазон температур °C | Перевірити `temperatureC` усіх елементів | Кожне значення в межах `[-20; 54]` |
| TC-06 | P1 | Допустимі значення `summary` | Звірити `summary` зі списком із розділу 1 | Значення належить множині з 10 дозволених рядків |
| TC-07 | P1 | Узгодженість °C ↔ °F | Для кожного елемента обчислити `32 + (int)(temperatureC / 0.5556)` | Результат збігається з `temperatureF` (допуск ±1 на округлення) |
| TC-08 | P2 | Swagger UI у Development | Відкрити `http://localhost:5052/swagger` | `200 OK`, відображається Swagger UI з ендпоінтом `/weatherforecast` |
| TC-09 | P2 | OpenAPI-схема | `GET /swagger/v1/swagger.json` | `200 OK`, валідний JSON, містить шлях `/weatherforecast` з методом `get` |
| TC-10 | P2 | Swagger вимкнено в Production | Запустити з `ASPNETCORE_ENVIRONMENT=Production`, відкрити `/swagger` | `404 Not Found`, при цьому `/weatherforecast` працює (TC-01) |
| TC-11 | P2 | Невідомий маршрут | `GET /unknown-route` | `404 Not Found` |
| TC-12 | P2 | Непідтримуваний метод | `POST /weatherforecast` | `405 Method Not Allowed` |
| TC-13 | P2 | Перенаправлення HTTP → HTTPS | Профіль `https`: `GET http://localhost:5052/weatherforecast` | Відповідь `307`/`308` з `Location` на `https://localhost:7034/...` |
| TC-14 | P3 | Випадковість даних | Виконати 10 послідовних запитів, порівняти значення | Значення `temperatureC`/`summary` відрізняються між запитами (не гарантовано для кожної пари — кейс інформаційний) |
| TC-15 | P3 | Smoke-перевірка продуктивності | 50 послідовних запитів `GET /weatherforecast` | Усі відповіді `200`, середній час відповіді < 200 мс |

Приклад перевірки кейсів TC-01…TC-07 однією командою PowerShell:

```powershell
$r = Invoke-RestMethod http://localhost:5052/weatherforecast
"count=$($r.Count)"
$r | ForEach-Object { "$($_.date) $($_.temperatureC)C $($_.temperatureF)F $($_.summary)" }
```

## 7. Критерії входу та виходу

**Критерії входу (entry criteria):**

- гілку зі змінами зібрано без помилок (`dotnet build`);
- застосунок успішно стартує на `http://localhost:5052`;
- доступна актуальна версія `Program.cs` (контракт ендпоінтів не змінювався під час тестування).

**Критерії виходу (exit criteria) — критерії приймання:**

- усі тест-кейси **P1** пройдено без дефектів;
- для тест-кейсів **P2** пройдено не менше 100 %, дефекти, якщо є, мають узгоджений обхідний шлях;
- відсутні відкриті дефекти рівня Critical/High;
- заповнено протокол виконання (розділ 8) і додано посилання на нього в описі PR.

**Стан на 2026-10-16:** усі критерії виконано — 15/15 тест-кейсів пройдено, відкритих дефектів немає.

## 10. Ризики та припущення

| Ризик | Вплив | Пом'якшення |
| --- | --- | --- |
| Відсутні автоматичні тести (юніт/інтеграційні) | регресії виявляються лише вручну | завести тестовий проєкт (xUnit + `WebApplicationFactory`) в одній з наступних ітерацій |
| Випадкова генерація даних | неможливо перевірити точні відповіді, лише інваріанти | перевіряти діапазони та узгодженість (TC-05…TC-07), а не конкретні значення |
| Дані не зберігаються, ендпоінт один | низьке покриття функціональності | розширювати тест-план разом із появою нових ендпоінтів |
| Різні версії .NET у команди | розбіжності у поведінці середовища | зафіксувати .NET 8 у `global.json` та в README |
| Залежність від локальних портів (5052/7034) | кейси не відтворюються на іншій машині | порти беруться з `Properties/launchSettings.json`, а не з пам'яті |
| У репозиторій закомічено каталоги `bin/` і `obj/` | шум у diff, ризик конфліктів під час злиття бінарних файлів | додати `.gitignore` для `bin/`, `obj/` і прибрати артефакти збірки з індексу окремим PR |

**Припущення:** перевірка виконується на локальній машині розробника, зовнішні залежності (БД, сторонні API) відсутні.
